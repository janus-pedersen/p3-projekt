\subsection{System-functionalities}
The system functionalities describe how Lapsus operates as a complete solution, from fall detection at the wristband level to alert delivery and user interaction through the application and backend services. The following diagrams illustrate how data flows through the system and how different components interact during normal operation and emergency scenarios.

\subsubsection{Fall detection algorithm}
The solution revolves around being able to detect the falls that the wearer of the device experiences. This algorithm should as mentioned, be able to differentiate between actual falls and other \gls{adl}'s.

\begin{figure}[H]
    \centering
\includegraphics[width=0.25\linewidth]{report//images/State Diagram.pdf}
    \caption{State diagram of the fall detection algorithm.}
    \label{fig:state_diagram}
\end{figure}

The designed algorithm consists of three \textit{states}, \verb|free-falling|, \verb|impact| and \verb|fall detected|. It uses this three step state machine to filter out some, but probably not all \gls{adl}'s. It works by first detecting a \verb|free-fall| state, where the wearer experiences a negative G-force, correlating with falling towards the direction of gravity. When the wearer is in this state, it await a high impact, that could be described hitting the ground or some other obstacle on their way down. If this is detected, the wearer is now in an \verb|Impact| state. If this impact is not detected within some set time period, the wearer is determined to not be falling and the state machine finishes. Once the impact has been detected, it waits for any more impacts, and if any arise, it will discard the state as being a fall, and contribute the forces to \gls{adl}'s (eg. boxing, washing dishes or other activities where the hands are involved). If no major motion is detected after the impact, it interprets it as if the wearer has landed from their fall, and the alert is sent out to the app and further on to their relatives.


\subsubsection{Data flow diagram}
The data flow diagram provides an overview of the system's processes.  At the top of the diagram, it is seen that the external entity 'User' sends the phone number and the corresponding code to the process 'Login'. To which the process 'Login' sends login information to the data store 'Users', which responds with the user profile. Process 2: 'Add/Remove relatives' gets the 'relative information' from the 'User'. The process then sends this data to the data store 'Relatives'. Process 3: 'Connect wristband'. Process 4: 'Cancel alert' receives the data 'press cancel on alert' from 'User' to which it establishes a \gls{ble} connection with the external entity 'Wristband'. 
Process 5: 'Store \gls{gps} location' sends the data '\gls{gps} coordinates' from 'User', sends the 'store location snapshot' to the data store 'Locations', which then sends the 'Receive stored data' to Process 8: 'View real-time \gls{gps}', where the display map is sent to the external entity 'Relative'. Process 6: 'Emergency alert' receives 'notify backend' from process number 9. After that, process 6 creates an alert, which is sent to the data store 'alerts' and process 7: send SMS alert. Process 7 then sends an SMS to the external entity called 'relative'. Process 8: View real-time \gls{gps} retrieves stored data from the data store 'location', then it displays the map to the external entity named 'relative'. Lastly, process 9 receives data regarding the accelerometer/gyroscope, and it then notifies the backend, specifically process 6.

\subsubsection{Sequence diagram}
The sequence diagram below describes the sequence when a fall is detected. The fall is detected by the wristband, which then notifies the mobile app. The mobile app creates the alert, and a new entry is created in the database in the backend. After this, the backend alerts the relative, where they can then respond to the alert. The ‘optional’ shows how a fall can be canceled by the user, in which case the mobile app cancels the alert, and the backend updates the corresponding database entry. After this, the backend notifies the relative, who can then contact the user regarding the canceled alert.

\subsubsection{Deployment diagram}
In the previous section, the workings of the wristband and application were highlighted. In the following deployment diagram, it is shown how all of these individual elements work together. The device 'wristband' runs the firmware and connects via Bluetooth Low Energy to the device 'user's smartphone' where the four components 'UI/Webview', 'Capacity API', Firebase SDK' and 'BLE API' run either in an Android or iOS environment. The user's smartphone connects to the cloud company Firebase/Google Cloud Platform through TCP/HTTPS (Firebase SDK). In the node 'Firebase/GCP', there is an artefact, the 'Firebase Functions' and a database, the 'Firebase Firestone'. The previously mentioned node connects via TCP and HTTPS to another cloud company called Twilio, in which the component 'Twilio API' is used. Lastly, this node connects with the relative's smartphone by the use of SMS/text messages.

Overall, the design of Lapsus aims to balance technical feasibility, user friendliness, and reliability. By separating sensing, processing, and notification responsibilities across the wristband, mobile application, and backend infrastructure, the system achieves a modular architecture that supports future extensions and improvements.
